**Create test/core/PoolInvariant.t.sol** — Stateful invariant testing using Foundry's invariant testing framework. The approach: create a Handler contract that performs valid random operations (swap, mint, burn) on the Pool, then define invariant functions that Foundry checks after each random call sequence.

Structure:
1. **PoolHandler contract** (defined in same file): Wraps Pool operations with valid bounds. Functions:
   - `addLiquidity(uint256 amount0, uint256 amount1)`: Bounds amounts, mints tokens, transfers to pool, calls mint
   - `swapToken0ForToken1(uint256 amountIn)`: Bounds amountIn, mints token0, transfers to pool, calculates output, calls swap
   - `swapToken1ForToken0(uint256 amountIn)`: Same in reverse direction
   - `removeLiquidity(uint256 fraction)`: Bounds fraction (1-100%), transfers that fraction of handler's LP to pool, calls burn

2. **PoolInvariantTest contract** (is Test):
   - setUp(): Deploy tokens, pool, handler. Add initial liquidity (1000e18 each). Record initial k. Use `targetContract(address(handler))` to tell Foundry which contract to call random functions on.
   - `invariant_constant_product_never_decreases()`: Get reserves, compute k, assert k >= initialK
   - `invariant_reserves_match_token_balances()`: Assert token0.balanceOf(pool) >= reserve0 and token1.balanceOf(pool) >= reserve1 (balances can exceed reserves due to direct transfers)
   - `invariant_total_supply_greater_than_minimum_liquidity()`: After first mint, totalSupply >= MINIMUM_LIQUIDITY
   - `invariant_dead_address_always_holds_minimum_liquidity()`: pool.balanceOf(0xdEaD) == MINIMUM_LIQUIDITY

**Create test/core/PoolReentrancy.t.sol** — Reentrancy attack tests using malicious ERC20 tokens.

Structure:
1. **MaliciousToken contract**: Extends ERC20. Has a `target` Pool reference and an `attackFunction` enum (SWAP, MINT, BURN). Override `transfer(address to, uint256 amount)`:
   - When target is set and transfer is being called BY the pool (detected via `msg.sender == address(target)` check), attempt to re-enter the target pool by calling the attack function.
   - Include a flag to prevent infinite recursion (attack once only).

2. **PoolReentrancyTest contract** (is Test):
   - Deploy malicious token as one of the pair tokens
   - test_should_prevent_reentrancy_on_swap: Set up pool with MaliciousToken + normal token. Add liquidity. Configure MaliciousToken to re-enter swap() during transfer callback. Execute swap. Expect revert with OZ ReentrancyGuard error selector: `bytes4(keccak256("ReentrancyGuardReentrantCall()"))`.
   - test_should_prevent_reentrancy_on_burn: Configure MaliciousToken to re-enter burn() during transfer callback. Transfer LP to pool, call burn. Expect revert.
   - test_should_prevent_cross_function_reentrancy_swap_to_mint: During swap callback, attempt to call mint(). Expect revert.
   - test_should_prevent_cross_function_reentrancy_swap_to_burn: During swap callback, attempt to call burn(). Expect revert.

**Key notes:**
- OZ v5 ReentrancyGuard uses custom error `ReentrancyGuardReentrantCall()`, not string revert
- The MaliciousToken needs to be compatible with Pool's constructor (must implement IERC20Metadata for name/symbol)
- The malicious transfer callback only triggers on transfers FROM the pool (outgoing transfers during swap/burn)
